# StoryWeaver 产品需求文档

文档状态：当前主文档  
目标版本：MVP 0.1～0.3  
最后更新：2026-08-13

## 1. 产品定位

StoryWeaver 是一个基于自研 Python Agent Runtime 的小说创作系统。系统把创作简报转换为可持续维护的小说项目，通过职责明确的专业 Agent 和确定性流水线完成建书、逐章创作、审查修订、状态结算和断点续写。

在小说创作闭环稳定后，系统可以从某个章节快照创建非正史沙盒，让用户与小说角色对话或观察角色互动。模拟结果默认不修改小说正史。

一句话目标：

> 让模型不只是生成一段正文，而是在受控计划、有限上下文和可验证故事状态下持续创作下一章。

## 2. 要解决的问题

直接使用裸模型续写小说时通常存在以下问题：

- 用户需要反复粘贴设定、大纲和前文。
- 上下文增长后，重要规则和早期事实容易被淹没。
- 人物位置、已知信息、物品和关系可能前后矛盾。
- 模型生成正文后，没有可靠机制同步伏笔、摘要和当前状态。
- 创作、审查和修订混在一个 Prompt 中，失败原因难以定位。
- 程序重启后难以从相同创作状态继续。

StoryWeaver 使用以下方式解决：

```text
创作简报
  → 小说基础设定
  → 章节计划
  → 受控上下文
  → 正文草稿
  → 审查与有限修订
  → 状态增量
  → 持久化与下一章
```

## 3. 产品范围和优先级

### 3.1 P0：原创小说创作

用户输入标题、题材、核心创意、主角、主要冲突、风格和目标篇幅。系统创建小说基础资料，并可以按章持续生成正文。

P0 必须支持：

- 从创作简报创建小说项目。
- 生成人物卡、世界设定、故事方向、创作规则和初始伏笔。
- 为下一章生成明确计划。
- 根据计划和有限上下文生成正文。
- 对正文执行结构化审查。
- 由确定性质量门禁决定接受、修订或拒绝，默认最多自动修订两轮。
- 从最终正文提取状态增量并校验后提交。
- 保存章节、摘要、伏笔、当前状态和审查结果。
- 关闭程序后重新加载项目并继续下一章。

### 3.2 P1：已有文本续写

用户导入短篇或少量章节，系统反推小说基础资料，按章节顺序重放并建立状态，随后使用和原创小说相同的写下一章流水线。

P1 首版只支持：

- UTF-8 TXT、Markdown。
- 单文件按“第 X 章”或 `Chapter N` 拆分。
- 一个章节一个文件的目录。
- 短篇或少量章节，不承诺处理任意长度整本小说。
- 导入结果可供用户查看和修正。
- 导入过程可以记录进度，失败后从指定章节继续。

### 3.3 P2：角色对话模拟

用户选择某个小说章节或当前状态，创建独立模拟会话。用户可以扮演角色、以旁观者输入事件，或者观察角色互动。

P2 必须遵守：

- 模拟从明确的小说状态快照开始。
- 角色只能读取该时点有权知道的信息。
- 每回合包含用户行动理解、世界变化提议、场景输出和状态提交。
- 模拟状态与小说正史状态隔离。
- 退出模拟时可以丢弃、保存为支线素材或导出记录。
- 将模拟结果写回正史属于后续人工确认功能，不在首版自动执行。

## 4. 非目标

MVP 暂不实现：

- 自动可靠解析任意长度 EPUB 或整本网络小说。
- 一次生成整本长篇并宣称质量稳定。
- 多个自治 Agent 自由讨论后自行决定工作流程。
- 复杂时间线知识图谱、向量数据库或图数据库。
- Web 账号、在线协作、计费和多租户。
- 自动发布生成内容。
- 图片、语音、视频生成。
- Skill、MCP 和外部研究工具。

这些能力不是永久排除，而是在小说创作闭环稳定前不进入主线。

## 5. 目标用户

- 希望把创意发展为连续章节的小说创作者。
- 希望在已有短篇基础上尝试续写的用户。
- 希望检查人物、伏笔和连续性的作者或编剧。
- 学习 Agent Loop、多 Agent 编排、Context 和 Memory 的开发者。

## 6. 核心用户流程

### 6.1 创建并连续写作

1. 用户填写创作简报。
2. Architect 生成小说基础资料。
3. 用户查看并确认基础资料。
4. 用户请求“写下一章”，可附带本章指令。
5. Planner 生成章节计划。
6. ContextBuilder 选择本章所需资料。
7. Writer 生成正文。
8. Reviewer 输出结构化问题。
9. 严重问题触发一次 Reviser；随后重新审查。
10. ChapterAnalyzer 从最终正文提取摘要和状态增量。
11. StateReducer 校验并提交状态。
12. ProjectStore 原子保存本章产物。
13. 用户继续下一章，或关闭后重新加载项目。

### 6.2 导入并续写

1. 用户提供 TXT、Markdown 或章节目录。
2. ChapterSplitter 识别章节。
3. FoundationExtractor 从有限内容反推基础设定。
4. 系统向用户展示提取结果。
5. ChapterAnalyzer 按章节顺序提取事实和状态变化。
6. 每章完成后保存进度和快照。
7. 导入完成后进入标准“写下一章”流程。

### 6.3 对话模拟

1. 用户选择小说和章节快照。
2. 系统复制角色、世界和信息边界到模拟会话。
3. 用户输入行动或对白。
4. 系统解释行动，提出并校验世界状态变化。
5. 系统生成角色反应和场景文本。
6. 本回合成功后一次性提交模拟事件和状态。
7. 用户退出时选择丢弃或保存模拟记录。

## 7. 专业 Agent 的职责

| 组件 | 职责 | 是否需要完整 Tool-Calling Loop |
|---|---|---|
| 顶层 Assistant | 理解自然语言意图并选择小说工具 | 后续需要 |
| Architect | 生成小说基础资料 | 否，有限 LLM 调用 |
| Planner | 生成下一章计划 | 否，有限 LLM 调用 |
| Writer | 根据计划和上下文生成正文 | 否，有限 LLM 调用 |
| Reviewer | 输出结构化审查问题 | 否，有限 LLM 调用 |
| Reviser | 针对审查问题修订正文 | 否，有限 LLM 调用 |
| ChapterAnalyzer | 从最终正文提取事实和状态增量 | 否，有限 LLM 调用 |
| Simulation Runner | 编排每个互动回合 | 由确定性代码编排 |

“多 Agent”在本项目中表示多个职责隔离的专业 Worker，共享模型适配和结构化协议，由 Pipeline 确定执行顺序；不表示让它们无限自由对话。

## 8. 功能需求

### 8.1 项目与基础设定

- `FR-PROJ-001`：系统必须使用稳定 `book_id` 创建和加载小说项目。
- `FR-PROJ-002`：建书失败时不得留下可被误认为完整项目的半成品。
- `FR-PROJ-003`：小说基础资料必须包含故事核心、人物、方向、规则和初始伏笔。
- `FR-PROJ-004`：用户必须能够查看模型生成的基础资料；人工编辑入口可以晚于首个 CLI 闭环。

### 8.2 章节生产

- `FR-CHAP-001`：系统必须根据已保存章节计算唯一的下一章编号。
- `FR-CHAP-002`：每章必须先形成 `ChapterPlan`，再生成正文。
- `FR-CHAP-003`：计划必须包含目标、必要情节点、禁止事项、参与人物和结尾方向。
- `FR-CHAP-004`：Writer 只能接收 ContextBuilder 选出的有限上下文。
- `FR-CHAP-005`：每章必须保存计划、正文、审查结果、摘要和状态增量。
- `FR-CHAP-006`：自动修订次数默认不超过一次。
- `FR-CHAP-007`：审查或状态提取失败时，不得污染已提交的小说状态。
- `FR-CHAP-008`：Web 写章必须先展示只读候选计划，用户明确确认后才能调用 Writer。
- `FR-CHAP-009`：用户必须能够通过自然语言反馈生成新的计划版本，也可以取消候选计划。
- `FR-CHAP-010`：候选计划必须记录作品基线章节；作品状态变化后不得继续执行过期计划。

### 8.3 Context 和状态

- `FR-CTX-001`：当前章节计划、硬规则、当前状态和相关未解决伏笔属于受保护上下文。
- `FR-CTX-002`：历史摘要和旧事件属于可筛选上下文，不得无限追加到 Prompt。
- `FR-CTX-003`：系统应记录本章实际选入了哪些上下文来源。
- `FR-STATE-001`：LLM 只能提出 `StoryStateDelta`，不能直接覆盖完整权威状态。
- `FR-STATE-002`：StateReducer 必须校验章节号、实体引用和状态转换。
- `FR-STATE-003`：每条事实、伏笔变化和人物变化必须记录来源章节。
- `FR-STATE-004`：重复事实不得无限累积。

### 8.4 审查和恢复

- `FR-REV-001`：Reviewer 必须至少检查计划遵循、人物一致性、信息边界、世界连续性和明显结构问题。
- `FR-REV-002`：问题必须包含类别、严重级别、说明和修改建议。
- `FR-REV-003`：修订前后都必须保留可追溯记录。
- `FR-REC-001`：程序重启后必须从最后成功提交的章节继续。
- `FR-REC-002`：失败重试不得重复提交章节或状态变化。

### 8.5 导入续写

- `FR-IMP-001`：系统必须将输入拆分为有序章节，并报告无法识别的格式。
- `FR-IMP-002`：系统必须按章节顺序建立状态，不能只分析最后一章。
- `FR-IMP-003`：导入进度必须可恢复。
- `FR-IMP-004`：导入完成后必须能复用标准章节生产流水线。

### 8.6 对话模拟

- `FR-SIM-001`：模拟会话必须基于不可变小说快照创建。
- `FR-SIM-002`：私有信息只允许所属角色读取。
- `FR-SIM-003`：失败回合不得部分修改模拟状态。
- `FR-SIM-004`：模拟默认不得修改小说正史。

## 9. 质量目标与评估

StoryWeaver 不承诺“文学质量必然高于裸模型”。MVP 需要证明的是流程控制、连续性、可恢复性和可观测性。

### 9.1 自动化指标

- 使用假模型完成全部核心单元测试，不依赖真实 API。
- 连续生成三章后，重启进程能够生成第四章。
- 章节编号、文件和状态提交无重复。
- Writer Prompt 不包含全部历史正文。
- 状态变化都具有来源章节。
- 关键计划项和禁止项可以通过确定性检查或结构化审查追踪。
- 私有信息隔离测试泄漏次数为 0。

### 9.2 对比评估

使用相同模型、参数和创作简报，对比：

```text
A：裸模型直接续写
B：StoryWeaver 受控流水线续写
```

人工盲评维度：

- 指令遵循
- 跨章连续性
- 人物一致性
- 情节完整性
- 可读性
- 平均耗时和 Token 成本

项目只报告实际测试结果，不预设 StoryWeaver 一定在所有文学维度胜出。

## 10. 发布定义

MVP 0.1 完成的标志是：

> 用户提供创作简报后，系统能够创建一个小说项目，连续生成三章；每章均具有计划、正文、审查、摘要和状态增量；程序重启后能够基于已保存状态生成第四章。
