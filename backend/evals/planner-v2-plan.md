# Planner V2 实现与对照验证方案

日期：2026-09-07。状态：待实现。

## 1. 本次决策

保留“作者要求 → Planner → Writer → Reviewer → 必要时修订 → Analyzer → 保存”的主流程。

第一轮只验证 Planner：保留旧版固定两阶段执行，新增基础资料更充分、允许按需检索的执行方式。先比较计划的准确性和成本，再比较接入相同下游流程后的正文。

本方案不承诺提升多少文学质量，也不预先承诺全流程 Token 降幅。判定目标是：Planner 成本下降，明确要求覆盖和事实准确性不退步。

## 2. Git 基线与提交安排

检查时的 HEAD 为 `0017d03`，分支为 `main`。此时工作区已经包含未提交的评测框架、生成预算和推理设置调整，因此 HEAD 本身不是本次评测代码的完整基线。

实施顺序：

1. 审阅并提交当前工作区，建议提交说明为 `chore: 保存小说评测与 Planner 优化前基线`。
2. 记录提交后的 SHA，作为 `baseline_commit`；在结果清单中另存运行时参数和依赖版本。
3. 从该提交创建工作分支，建议名为 `feat/planner-v2-adaptive`。
4. 后续代码按“观测与实验夹具”“V2 执行器”“V2 上下文与接入”“对照验证”拆分提交。

这些是建议操作；本方案文件的创建不会自动提交、切分支或推送。

`backend/evals/results/` 已被忽略，基线提交不包含既有运行产物。保留这些本地结果用于对照；数据库状态、环境参数和依赖环境也不会由 Git 提交自动保存，实验需要单独冻结。

## 3. 两个版本的边界

| 项目 | V1：旧版 | V2：新版 |
| --- | --- | --- |
| 初始输入 | 当前最小资料与索引 | 原始要求、当前框架、相关状态和事实内容、近期摘要 |
| 执行方式 | Research → EvidencePackage → Report | 同一循环内选择查询或提交 |
| 直接交付 | 固定研究后交付 | 第一次调用可提交有效计划 |
| 工具 | 现有只读工具 | 先复用相同工具和底层数据 |
| 输出 | ChapterPlan | 相同 ChapterPlan |
| 默认版本 | 保留为默认 | 仅显式启用 |

共用 `PlannerAgent`、工具实现、计划输出 Schema 和领域校验器。使用内部策略或执行模式选择分支，避免复制两份业务 Agent。建议配置字段为 `planner_mode`，取值 `legacy_two_phase` / `adaptive_v2`，非法值在调用模型前拒绝。

生产默认值保持 V1。V2 失败时在实验中记录失败，不自动重跑 V1 掩盖失败率或追加成本。以后是否加入生产回退策略单独决定。

## 4. 工作包 A：可复现输入与用量观测

### 4.1 冻结 Planner 输入

每个案例保存：

- 当前作品基础资料与已提交状态。
- 章节摘要、原始作者要求、批次规划上下文和实际启用的 Skill 快照。
- 作品版本、当前章节号、输入哈希与代码提交 SHA。
- 模型、温度、推理设置、超时、输出上限、检索和上下文预算。

两种 Planner 必须读取同一份不可变快照；不得让 V1 先改变状态，再让 V2 使用改变后的状态。隐藏评分要求不进入生成输入或检索工具。

已有评测导出的最终正文不足以重建完整 Planner 历史状态。优先从已保存检查点或上下文快照取得；拿不到时构造明确标注的测试夹具，不能声称它是原运行的精确重放。

### 4.2 用量

复用 `WorkerRunMetric` 和模型事件，增加按章节、角色、版本落盘的明细：实际模型请求序号、成功状态、输入/输出 Token、耗时、检索次数、命中与未命中、重复查询、格式修复、网络重试、是否直接完成。

核对 `MODEL_COMPLETED` 与 `MODEL_REPAIRING` 的计数边界，避免同一次请求既计为完成又补计为修复。失败请求没有返回 usage 时标记未知，不能假装费用为零。真实请求次数与已获得 usage 的请求次数分别记录。

验收：请求明细、角色汇总、章节汇总可核对；失败和修复路径也有测试覆盖。

## 5. 工作包 B：V2 基础上下文

### 5.1 直接提供的内容

1. 作者原始要求：完整保留，不以 Planner 的转述替代。
2. 当前章节大纲、批次边界、全局写作硬规则、故事核心方向。
3. 时间、地点、最后提交章节。
4. 与作者要求和当前框架明确相关的人物：稳定限制、当前状态、持有物、相关知识依据。
5. 相关关键事实：包含 `value`、来源章节和有效状态，不只传事实 ID。
6. 最近一章摘要、需要推进的相关伏笔内容。
7. 其他人物和历史资料的有限索引，以及缺失、冲突、截断说明。

初始人物选择不能依赖尚未生成的章节计划。先利用作者提示、当前框架、当前视角角色、实体别名和已有关系做确定性选择；不确定时保留索引供模型补查。关键词匹配不等于完整语义理解。

新方案首轮不额外引入模型调用来筛选资料或生成摘要。也不让所有角色读全部历史正文。

### 5.2 预算

使用现有初始预算作为起点，先去除重复表示，按相关性装配。保存必需内容、已选内容和被排除内容的占用，不预先把预算统一加大。

原始要求和已确认必需的硬约束不能静默删除。必需内容超预算时显式失败并记录组成；如确需调整预算，应作为单独实验参数记录。

验收：能识别出的关键人物限制、事实值和来源进入模型输入；无关历史不因“重要性高”无限挤占上下文；批次最后一章与非最后一章的边界保持正确。

## 6. 工作包 C：可选择检索或提交的执行器

建议新增 `backend/src/storyweaver/llm/adaptive.py`，提供通用执行函数。V1 的 `two_phase.py` 保留。

循环行为：

```text
基础上下文 + 只读工具 + submit_plan
    ↓
模型响应
    ├─ 查询：执行有预算限制的工具 → 保留结果 → 下一轮
    ├─ 提交：结构和领域校验 → 合格后结束
    └─ 无有效动作：有限修复或明确失败
```

必须实现：

- 第一次调用可直接交付；不附加一个固定的 Report 调用。
- 工具调用和提交是协议动作，提交成功不修改数据库或批准计划。
- 参数校验、去重、超时、工具重试复用现有 `tool_runtime.py`。
- 提交必须先通过 Schema、章节号、实体/伏笔引用、计划领域规则校验。
- 格式修复保留已获得证据，不从第一轮重新检索。网络重试和领域修复分别设限。
- 未通过校验的提交不能触发成功终止。多次提交、同一响应混合查询与提交必须有显式规则：未完成查询不能成为本次计划的证据。
- 预算耗尽前预留交付机会；无法确认的必要历史事实不能被编造。以类型化“依据不足”失败返回，保存诊断，不强行输出看似有效的计划。
- 保留取消、超时、失败事件与上下文快照。

### 6.1 合并后的预算

当前 ContextBudget 用两个隔离阶段的峰值计算。V2 必须计算真实同轮峰值：系统说明、工具 Schema、初始上下文、历史调用/结果、输出预留和安全余量。

每轮请求前检查预算；累计工具结果预算和单条结果预算同时生效。证据不得同时以完整工具历史和重复 EvidencePackage 两种形式发送。必要时程序确定性去重、选择，不额外调用模型压缩。

### 6.2 推理参数

V1 Research 与 Report 当前使用的推理设置可能不同。V2 合并后不能声称与 V1 每一阶段完全等价。首轮明确记录有效参数，初始决策和检索后续轮次沿用既定 Worker 参数，修复采用明确的修复策略；不同时调整模型、温度和输出上限。

整体比较用于判断 V2 是否值得用。如需归因到上下文或推理强度，再另做小范围消融实验。

## 7. 工作包 D：接入 Planner，保持下游边界

涉及文件：

| 文件 | 计划变更 |
| --- | --- |
| `novel_creation/agents/planner.py` | 按模式选择上下文和执行器；移除 V2 的固定检索顺序提示 |
| `novel_creation/planner_context.py`（建议新增） | V2 上下文选择、缺口说明和来源记录 |
| `llm/adaptive.py`（建议新增） | 查询/交付循环和有限修复 |
| `llm/__init__.py` | 导出新执行入口 |
| `context/policy.py` | 模式对应的预算校验，兼容 V1 |
| `novel_creation/application.py` | 注入显式模式，默认仍为 V1 |
| `novel_creation/observability.py` | 版本、阶段、真实调用和检索统计 |
| `evaluation/` | 快照重放、对照输出、原始证据和指标落盘 |

V2 系统提示不再写“初始上下文只有索引”或强制“先读取最近摘要”。实际信息充分时直接规划；缺少具体历史依据才查询。

`ChapterPlan` 的领域契约首轮保持一致，诊断、来源和检索轨迹存入侧边元数据。Writer、Reviewer、Analyzer 不切换模式，质量门禁不顺便修改。

注意：当前检索只有事实和摘要，没有历史正文片段。首轮先验证已有工具能够回答的缺口，无法回答的案例记录为依据不足。原文片段工具列为后续独立工作包，不能用想象的工具能力解释实验结果。

Planner 证据向 Writer 传递也是后续单独验证项。首轮下游对照保持现有输入机制，明确它的局限，避免同一实验同时改 Writer。

## 8. 工作包 E：测试与对照实验

### 8.1 自动化测试

覆盖以下行为：

1. 信息充分，一次调用直接提交，零检索。
2. 缺少可检索事实，查到证据后正确提交。
3. 索引与当前状态冲突，识别并核对来源。
4. 未命中、截断、预算耗尽：不凭空生成必需历史事实。
5. 非法 ID、错误章节号、格式错误：校验失败不算成功，修复不重复检索。
6. 重复查询、并行查询和查询/提交混合响应的边界。
7. 工具累计结果和模型对话历史超预算。
8. 超时、取消、网络重试与指标准确性。
9. V1 默认路径和原有测试不退步。

优先扩展 `test_context_policy.py`、`test_sdk_novel_workers.py`、`test_novel_observability.py`、`test_evaluation.py`，新增 `test_adaptive_planner.py` 等必要行为测试。

### 8.2 Planner 离线对照

建议先冻结 6 类快照，每类 3 组配对运行，即两版共 36 次 Planner 执行；这是待执行实验规模，不自动启动付费调用。

案例至少包含：资料充分、实体状态缺失、明确要求覆盖（参考第 3 章）、隐藏物件来源（参考第 9 章）、物品归属冲突、结尾/批次揭晓边界。

两个版本交替运行，避免固定顺序影响服务端缓存和延迟。比较相同底层事实与要求；初始可见内容差异是方案的实验变量。检索底层数据相同。

分别检查作者要求是否进入计划、历史事实是否有依据、知识边界和物品归属是否正确、计划是否足以执行。每个错误要有原始要求或历史证据支持，不能只看模型整体偏好分。

保留每次计划、输入、工具结果、校验结果、用量和原始判断。新版本失败不能从成本分母中删除。

### 8.3 预先固定的初筛门槛

以下是建议的工程验收门槛，应在真实实验前冻结，不是性能承诺：

- 必须通过全部确定性行为测试。
- 资料充分案例必须展示有效的一次调用直接提交路径。
- 人工核实的严重历史编造、提前揭密不能新增。
- 作者要求遗漏和有效计划失败次数不得高于 V1；样本不足或差异不稳定时只报告不确定，不宣布等价。
- 配对样本整体 Planner Token 至少下降 20% 才进入下一阶段；同时报告中位数、最差案例和全部失败成本，不能只展示最好案例。
- 耗时和重复检索需要报告，但缓存、网络波动导致的延迟变化不单独作为胜负依据。

如未达标，保留 V1 默认，依据具体失败类别修改 V2；不继续迁移其他 Agent。

### 8.4 下游与完整运行

Planner 初筛通过后，把两版计划分别交给参数和实现相同的下游流程，使用隔离副本从同一章起点生成，检查最终正文是否出现新增遗漏或冲突。

之后才做完整连续章节运行。各分支后续会形成不同历史，应如实报告这是端到端实验，而不是每章输入严格相同的重放。第 12 章已有 Analyzer 预算故障应单列为公共下游问题，不能把它归因于 Planner 或悄悄在某一分支修复。

质量评估保留详细作者提示和强裸模型基线。已知 Judge 问题（轮次分歧与平局混合、首轮均分、胜者与理由矛盾、字符分母）单列修正；统计口径改变需重算双方，不与 Planner 优化效果混为一谈。

## 9. 后续范围与停止条件

只有 Planner 通过验收，再考虑 Reviewer（包括修订复查）、Analyzer 复用新执行器。各角色分别定义上下文和验收，不一次性开启。

后续单独评估：历史原文片段工具、Planner 证据传递给 Writer、Reviewer 明确要求逐项核对、Analyzer 事实去重和预算恢复。

出现新增严重事实错误、成本无收益、失败率增加时停止推广。回滚以模式切回 V1 为主，不删除已提交章节或评测产物。
